# Persistent no-action terminal projection

Task 3 adds a terminal result for a strictly clean, context-less no-action agent run and replays it from memory or persisted state. The DTO excludes the normal context, proposal, evidence-reference, and expiry fields, while the coordinator returns it before starting another runner and accepts proposal-free replay. The persistence dispatcher distinguishes the two terminal payload schemas by exact field set, but it does not validate the persisted session envelope against the selected terminal variant. The unchanged MCP context tool retains a return annotation that excludes the new terminal type, leaving its public contract narrower than the changed runtime behavior. Watch for: **confirmed** persisted no-action sessions can retain a context or proposal; **likely** MCP clients/schema generation will not model the terminal response.
**Verdict**: NEEDS_CHANGES

## High-level view

The inner no-action payload has the intended narrow shape, but `_StoredHostSession` treats all terminal lifecycles alike. A syntactically valid persisted no-action payload can therefore be combined with a valid persisted context or proposal and still load, defeating the no-context/no-proposal terminal boundary.

The coordinator return type includes the new terminal, but the MCP entry point is still typed as context-or-failure. This creates an API-contract mismatch exactly on the path that now returns terminal data from `riskprobe_get_decision_context`.

## No-action terminal state can be persisted as a context/proposal hybrid

**confirmed** — `_StoredHostSession.validate_lifecycle_payload` only requires a terminal session to have an outcome and no failure. It permits `context` and `proposal` regardless of whether `outcome` deserializes as `HostDecisionOutcome` or `HostDecisionNoActionOutcome`. `_outcome_from_payload` rejects hybrid *inner* outcome fields, but `_session_from_stored` then accepts an exact no-action payload contained in an outer session that also holds a valid context and/or proposal.

This is a fail-open persistence boundary: a modified or corrupted session can replay an ostensibly context-less terminal while retaining the context/proposal association the terminal contract forbids. The added tests cover a hybrid outcome dictionary, but not a hybrid stored session followed by coordinator construction/replay. Make lifecycle validation inspect the terminal discriminator/payload and require no context or proposal for no-action.

## MCP tool signature does not express the new terminal response

**likely** — `riskprobe_get_decision_context` is annotated as `HostDecisionContext | HostDecisionFailure`, although `HostDecisionCoordinator.get_context()` can now return `HostDecisionNoActionOutcome`. Its implementation passes that object through unchanged. If the MCP library derives an output schema from the annotation, clients cannot discover or validate the `terminal_reason: "no_actionable_diagnosis"` response; even without generated validation, the declared Python API is false.

Import the no-action DTO and widen the tool return union. Existing MCP tests cover normal context, normal terminal, and failure responses, but not this new response.
