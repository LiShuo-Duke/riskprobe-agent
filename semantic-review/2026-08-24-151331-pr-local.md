# Auto fallback clears validation snapshot evidence

The Task 6 round-one fix separates a requested time-validation mode from whether time validation was actually applied. When `auto` cannot produce three usable, two-class chronological partitions, the persisted data profile now removes `snapshot_min` and `snapshot_max`; a successful chronological `auto` split retains them. The same applied flag now drives validation inputs, evidence payloads, metadata, manifest identity, split labeling, and report rendering. Watch for: no new severe or important issue identified in this review. Original finding: **ADDRESSED** (confirmed).

**Verdict**: APPROVED

## High-level view

The service establishes the applied state before allocating the run and recomputes it from the same stable snapshot while partitioning. This makes the artifact binding, the validation mode, and the declared split strategy describe the path actually used rather than merely the configured `auto` request.

Fallback writes a snapshot-free public data profile, while strict chronological success retains the profile range. Report rendering receives the applied state explicitly, so it cannot infer time validation from a stale in-memory profile range.

## Applied validation state is the single artifact contract

`RiskProbeService.run()` determines whether `auto` has usable chronological Train/Test/Holdout partitions before creating its `RunContext`, then binds `time_validation_enabled`, `time_validation_mode`, and `time_validation_applied` into the manifest identity. The partition stage only retains profile snapshot bounds when that applied state is true. Therefore the fallback profile cannot advertise an OOT time range, while strict or usable-auto runs retain the dates needed to substantiate chronological validation.

The same applied state selects snapshot-free projections and disables time decay in rule validation and local-rule discovery. `evidence_cards.json` consequently records non-time validation on fallback, and metadata/manifest both record `time_validation_applied: false` with `auto_stratified_fallback`; successful auto uses `true` with `time_group_split`.

## Report cannot re-enable time validation from profile dates

The renderer takes `time_validation_applied` explicitly. This avoids treating snapshot values as proof that validation occurred, and suppresses the snapshot-range and time-validation language for auto fallback even though the private in-memory profile still contains dataset dates. The fallback limitation is included in both metadata and the report.

## Targeted coverage

`test_auto_time_split_uses_strict_oot_when_every_partition_has_both_targets` verifies retained snapshots plus applied metadata and manifest values. `test_auto_time_split_falls_back_to_stratified_non_oot_validation` covers one-date, two-date, and single-class chronological layouts; it verifies cleared snapshots, disabled validation inputs and evidence fields, metadata/manifest applied values, fallback strategy, and absence of report snapshot/time-decay claims.
